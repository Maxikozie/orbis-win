# Handoff — Fallout NV texture mapping and split runtime build (2026-11-02)

## Current finding

The Fallout New Vegas gameplay screenshot showed large missing black textures.
The active PS4 log `build-ps4-logs/ps5log-20261028-085250.log` records repeated
failures during D3D9 texture initialization:

```text
map_file_into_view unaligned shared mapping ... not supported
virtual_map_section mapping ... failed
Mapping non-persisted file failed: 87
D3D9: InitTexture: map failed
D3DXCreateTextureFromFileInMemoryEx Texture creation failed.
```

This gives a direct mechanism for missing textures. The existing 0602 fix
handles unaligned writable shared sections while mapping PE images; the failing
call here goes through the general `virtual_map_section()` file mapping path.
The log's guest address is only Windows-page aligned, not host-page aligned.

## Patch and intended scope

Added `src/wine-patches-ps4/1024-ntdll-private-copy-unaligned-committed-mappings.patch`.
For an unaligned writable view, it keeps the current rejection for persistent
file mappings. For `SEC_COMMIT` pagefile-backed views only, it allows Wine's
existing `mprotect` + `pread` path to populate a process-local copy. This avoids
changing aligned mappings or shared writes to persistent files. The new log
line is `unaligned committed mapping ... using private copy`.

Hardware confirmation is still pending. On the next Fallout NV launch, check
that these mappings report the new private-copy line and that the paired
`D3D9: InitTexture: map failed` / D3DX texture-creation failures stop. Revisit
the section flags if the current errors continue on `SEC_FILE` mappings; do not
broaden the fallback to persistent files without evidence.

```sh

scripts/prx-ps4.sh
scripts/radv-prx-ps4.sh
scripts/freetype-prx-ps4.sh

PW_SPLIT_RUNTIME=1 TITLE_ID=GLDS10044 \
  TITLE='Prospero Wine Split Runtime Texture Map Fix' \
  PKG_OUT=/home/zpeirce/ps4-gladius/pkgout/fnv-texture-map-1024 \
  PKG_BASE_OUT=/home/zpeirce/ps4-gladius/pkgout/fnv-texture-map-1024-base \
  scripts/build-relocatable-wine-ps4.sh
```

This produced the small relocatable app/profile update and a full base-stage
package. The exact installer filename is
`IV0000-GLDS10044_00-GLDS100440000000.pkg` in both output directories. The
small app package is 6,619,136 bytes (SHA-256
`13b5e676a4ce5fbd7efcd7131e49574fa1edc1ebf7428c91231e9a74e4e055aa`) and was
uploaded as `/data/pkg/wine-app.pkg`; it was retrieved and hash-checked. The
425 MiB base package remains local at
`pkgout/fnv-texture-map-1024-base/IV0000-GLDS10044_00-GLDS100440000000.pkg`.

**Split runtime deployment correction:** the runtime path is loaded with
`sceKernelLoadStartModule()` (see `src/native/pw_wine_dl_ps4.c`), so it must
contain the generated PS4 module wrapper from
`prospero-win/.deps/wine-ps5/prx/sce_module/ntdll.prx`. The build copies that
exact file into `pkg-stage/win/wine/lib/wine/x86_64-unix/ntdll.prx` and the
installed package uses that path. Do **not** copy `ntdll.shared.elf` or
`ntdll.oelf` directly into the split runtime directory.

The initial direct runtime update used `ntdll.shared.elf` (SYSV OSABI), then
`ntdll.oelf` (raw FreeBSD ELF); both produced `load status=-2147352568 stage=1
module=0x80020008 segments=0` and returned to the launcher before Wine began.
An upload acknowledgment alone was not enough to verify the runtime file: the
FTP server later returned different bytes for the canonical path. The bad live
override was removed and RETR confirmed it absent, so a fresh launch falls back
to the installed app's `/app0` runtime. The preserved generated module is
1,061,632 bytes, SHA-256
`62bbfd8540e3ca67a5f7ccd6e24f3e1b6654022270e7ce7b0424740505b59d63`.

The corrected full relocatable package was uploaded to `/data/pkg` and
readback-hashed before the bad `/data` override was removed:

```text
IV0000-GLDS10044_00-GLDS100440000000.pkg
SHA-256 f0e08c7171467849dc8144bd2efa35043cd9273a4cf6a6f8fab46fe67f8609f2
```

After installing this package, launch Fallout NV and check the log selects the
packaged fallback, e.g. `/app0/win/wine/lib/wine/x86_64-unix/ntdll.prx`, then
check whether the new `unaligned committed mapping ... using private copy`
diagnostic appears and D3D texture creation failures stop. No hardware result
for this fallback has been collected yet.

The valid path for a direct split runtime update, if retried, is:

```text

```

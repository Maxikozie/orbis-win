# Handoff — Fallout NV texture mapping and split runtime build (2026-11-02)

## Current finding

The Fallout New Vegas gameplay screenshot showed large missing black textures.
The active PS4 log `build-ps4-logs/ps5log-20261028-085250.log` records repeated
failures during D3D9 texture initialization:

```text
map_file_into_view unaligned shared mapping ... not supported
virtual_map_section mapping ... failed
Mapping non-persisted file failed: 87
D3D9: InitTexture: map failed
D3DXCreateTextureFromFileInMemoryEx Texture creation failed.
```

This gives a direct mechanism for missing textures. The existing 0602 fix
handles unaligned writable shared sections while mapping PE images; the failing
call here goes through the general `virtual_map_section()` file mapping path.
The log's guest address is only Windows-page aligned, not host-page aligned.

## Patch and intended scope

Added `src/wine-patches-ps4/1024-ntdll-private-copy-unaligned-committed-mappings.patch`.
For an unaligned writable view, it keeps the current rejection for persistent
file mappings. For `SEC_COMMIT` pagefile-backed views only, it allows Wine's
existing `mprotect` + `pread` path to populate a process-local copy. This avoids
changing aligned mappings or shared writes to persistent files. The new log
line is `unaligned committed mapping ... using private copy`.

Hardware confirmation is still pending. On the next Fallout NV launch, check
that these mappings report the new private-copy line and that the paired
`D3D9: InitTexture: map failed` / D3DX texture-creation failures stop. Revisit
the section flags if the current errors continue on `SEC_FILE` mappings; do not
broaden the fallback to persistent files without evidence.

## Post-1026 FNV crash: `pread` on unseekable descriptor (2026-11-02)

The post-1026 test window produced a new first-fault record at PS4 time
`10:16:44.318`. The app trace in
`/home/zpeirce/codex_scratch/fnv-texture-map/run-after-1026-push-20261102/`
shows an unaligned committed mapping at `0x1a800000-0x1a900000`; the 1 MiB
private-copy fallback then fails its first `pread` at offset `0x3400000` with
`errno=29 (ESPIPE)`. Earlier attempts in the same run hit ESPIPE at offsets
`0x1000000` and `0x100000` too.

At the same timestamp, the first guest AV is a write at runtime EIP
`0x7b84779b` in the package i386 `msvcrt.dll` memset routine. Registers are
`EBX=0xc340`, `ECX=0x15570`, `EAX=0`; the instruction is a vector store through
EBX. This confirms the immediate fault is an invalid low memset destination.
The failed mapping is temporally adjacent, but causality is not yet established.
The package hash selected by this launch was not recorded, so do not claim the
console definitely installed 1026 merely because that package had been pushed.

The crash dialog identified
`GLDS10044_1793643405.sorbisdmp`; exact-path FTP retrieval returned 550 after
100 retries. No encrypted dump was obtained. The usable diagnostic records,
matching executable disassembly, and run notes are retained under the path
above. This resembles the prior Fallout 3 low-address memset after a failed
unaligned mapping in `docs/HANDOFF-2026-10-26.md`, but that earlier run did not
identify ESPIPE or prove causation.

Patch `1027-ntdll-log-file-map-fd-on-pread-failure.patch` is an observation-only
change. It preserves the original mmap errno and, only when fallback `pread`
fails, records `F_GETFL`, `fstat` mode/size/device/inode, and `lseek(SEEK_CUR)`.
It does not alter the fallback, descriptor position, or guest behavior. Use
these fields to identify the descriptor class and whether mmap selected the
fallback before deciding on a behavioral fix. Keep the full relocatable
package, native CPU profile, and 1026 fault-context kernelbase diagnostics.

Built 1027 as an observation-only follow-up from the exact 1026 package stage.
The only changed payloads are the two matching Unix NTDLL PRX copies:
`sce_module/ntdll.prx` and `win/wine/lib/wine/x86_64-unix/ntdll.prx`. All other
1,793 staged files, including the relocated app PRX, CPU-native profile, and
1026 i386 exception diagnostics, are unchanged. The NTDLL now logs its original
mmap errno and, only after fallback `pread` fails, descriptor flags, fstat
mode/size/device/inode, and current seek position. This does not attempt to
repair the mapping or change gameplay behavior.

## Fallout: New Vegas comparison

Fallout was selected from the launcher using the existing console profile
`fallout-new-vegas` and prefix `/data/prospero-win/prefixes/fallout-new-vegas`.
The runtime reported `cpu=native prefix_cpu=1`. It loaded `FalloutNV.exe` and
the game's native `d3d9.dll`, but produced no frames. About 21 seconds after
startup, the console recorded a `SIGSEGV` (signal 11), a user read from the
unmapped address `0x0000000fffffff40`, and Wine's `ntdll.prx` signal path. The
runtime also logged `wgl:internal_context_create Failed to create internal
thread context` before the fault. Flexible memory was still about 260 MiB and
`dmem_failures=0`, so this was not an observed memory-allocation failure.

The crash reporter completed a core dump, then deleted it during its cleanup;
the klog remains in the local ignored `build-ps4-logs/` directory. The exact
faulting game/runtime call still needs a core or better signal-context trace.
The console profile differs from the older checked-in
`src/profiles/falloutnv.profile` (`fallout-new-vegas` versus `falloutnv`), and
the console profile had no `[runtime] cpu` key. The runtime defaults PE32 DXVK
titles to native WoW64, which matches the observed `cpu=native`. A controlled
translator profile is now ready at
`/data/prospero-win/profiles/fallout-new-vegas-translator.profile`. It keeps the
same executable, existing `fallout-new-vegas` prefix, DXVK overrides, display,
and input; only the profile ID/name and explicit `[runtime] cpu = translator`
differ. It was uploaded with the minimal GoldHEN FTP client and read back
byte-for-byte. The existing package already supports this setting, so no
package rebuild was needed.

## Important runtime caveat

The translator comparison was then run. Runtime logs confirmed
`profile=fallout-new-vegas-translator` and `cpu=translator prefix_cpu=-2`.
Fallout still produced no frames and crashed with SIGSEGV. Just before the
fault, `FalloutNV.exe` attempted to create `FalloutNVLauncher.exe`; this runtime
returns `STATUS_NOT_SUPPORTED` for `NtCreateUserProcess`. The following
`NtQueryInformationProcess` path faulted in syscall `0x2c` at guest address
`0x8033729a0`. DXVK initialized, memory logs showed about 246 MiB flexible free
and zero dmem allocation failures. The dump
`/user/data/sce_coredumps/GLDS10078_1792539031/GLDS10078_1792539031.sorbisdmp`
was created, then deleted by the console crash reporter before it could be
retrieved. This confirms the failure also occurs with translator selected, but
the exact underlying fault still needs a preserved dump or deeper syscall
trace. The attempted child launch is a concrete lead: determine why this
installation's `FalloutNV.exe` starts the launcher and whether the game can be
started without child-process creation before changing the runtime's general
process-creation policy.

## Next useful test

For Fallout, first establish whether the `FalloutNV.exe` →
`FalloutNVLauncher.exe` child launch is expected for this exact install and find
a game-side way to bypass it. Do not enable general child-process creation as a
quick workaround: the port explicitly returns `STATUS_NOT_SUPPORTED`, and a
real implementation needs its own PS4 process model. If another run is needed
for the fault, retrieve the coredump before the crash reporter removes it. Keep
the known-good Oblivion profile and music-disabled setting intact.

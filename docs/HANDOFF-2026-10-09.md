# Handoff — GTA IV on PS4 Pro, the Neo-only GPU hang (2026-10-09)

Written for whoever picks this up next. The console is at 10.168.2.52.

## Do not probe the console

Deploy with `scripts/deploy.sh` only. For files, use `scripts/ftp-get.py` /
`ftp-put.py` **on known paths**. Never list directories, never scan ports, never
run `scripts/preflight.sh` (it probes 2121/1337/21) and never `logs.sh klog`
(its `need_console` probes). Start receivers by invoking `log-receiver.py` /
`ps5logd.py` directly. **An FTP login kills GoldHEN** — `scripts/ftp-*.py` send
no login, which is why they are the only safe tools here.

## The one-line state

A Neo build hangs the GPU at the first mission's intro cutscene; the same code
built without `--neo` plays through it. Three runs today produced the first hang
dumps this project has ever had. They narrow the fault a long way but **do not
identify it**, and the most promising hypothesis has **not actually been tested
yet** — the experiment misfired. That is the first job.

## START HERE: the raster-config experiment did not run

`src/mesa-patches-ps4/0004-gladius-four-se-raster-config.patch` changes
`CHIP_GLADIUS`'s `raster_config` from `0x2a00161a` to `0x3a00161a`. It is applied
in the working checkout and **it is in the shipped binary** — `libvulkan_radeon.a`
contains both the new constant and the `ORBIS_RASTER_CONFIG` knob string.

**But the value never reaches the register.** The run's `radv.log` still shows
`2a00161a` six times and `3a00161a` zero times, and the command stream still
carries:

    c0026900 000000d4 2a00161a 0000002e

`SET_CONTEXT_REG` offset `0xd4` is `0x28000 + 0xd4*4 = 0x28350` =
`R_028350_PA_SC_RASTER_CONFIG`, and the next dword is `PA_SC_RASTER_CONFIG_1`.
So the preamble is still programming the old pair.

The run after that patch crashed the same way — **which proves nothing**, because
the thing under test was never active.

Two candidates, neither checked:

1. `src/amd/common/ac_cmdbuf.c:233` writes `info->pa_sc_raster_config` directly,
   but **line 237 calls `ac_write_harvested_raster_configs()` instead** when render
   backends are harvested. That path recomputes per-SE values and may not use the
   value `ac_get_raster_config()` produced. Read `ac_cmdbuf.c:225-245` and find
   which branch this part takes — `enabled_rb_pipes_mask` is `0xff` here with
   `num_rb_pipes = 8`, so the harvested path is plausible.
2. Something overwrites `info->pa_sc_raster_config` after `ac_gpu_info.c:2006`
   sets it.

A cheap first check that needs no rebuild: set `ORBIS_RASTER_CONFIG=0x3a00161a`
in `/data/prospero-win/radv.env` and see whether the stream changes. If it still
does not, the override is being bypassed downstream and candidate 1 is the
answer.

Only once the stream shows `3a00161a` is the hypothesis testable.

## Why raster config is the suspect

`ac_gpu_info.c` says it itself, in the `CHIP_GLADIUS` arm:

> THIS PAIR IS INTERNALLY INCONSISTENT AND IS CARRIED ANYWAY [...] raster_config's
> high half is the TWO-shader-engine shape (>> 24 == 0x2a, as Tahiti's), while
> raster_config_1 is Hawaii's FOUR-engine SE_PAIR_MAP [...] the 4-SE entry pairs
> 0x3a00161a with 0x2e. The Linux stack this came from also reports max_se = 4 for
> Gladius, which would make the high half wrong rather than the low one.

And `ac_orbis_drm.c`'s Gladius arm predicted the symptom: *"If geometry corrupts
on screen, that pair is the suspect."* That arm reports
`num_shader_engines = 4` on a Pro (`orbis_is_neo ? 4 : 2`), so the part is being
described as 4-SE while the rasterizer is programmed with the 2-SE shape.

It fits every observation:

* **Neo-only.** Base PS4 is `CHIP_LIVERPOOL`, whose pair (`0x2a00161a` / `0`) is
  self-consistent for 2 SEs. That is the build that plays the cutscene.
* **Graphics-only.** A rasterizer told to distribute primitives across shader
  engines that are not mapped waits on a backend that never answers.
* **Clean addresses.** Nothing is wrong with where the CP was sent (below).
* **Appears under geometry load**, not in menus.

It is a hypothesis, not a finding. Treat it as one.

## What the dumps actually establish

Across all dumps in all three runs, without exception:

* The stop is in a **PS and a VS**. No HS, ES or GS in any dump.
* The CP's address audit is **clean**: `0/372`, `0/256`, `0/12`, `0/8` DMA_DATA
  addresses not in a live mapping; `0` unmapped `SET_BASE`; `0` unmapped shader
  user-data pointers; `0` unmapped SET_PREDICATION or write targets. The driver's
  own wording: *"the fault is in what it READ rather than in where it was told to
  look."*
* **Zero syscall faults** anywhere.

## The kill is Sony's watchdog, not our timeout

From klog at the moment of death:

    12:38:01.157 [SceLncService] Killing Shell UI since HP3D has timed out.
    12:38:01.157 [SceLncService] KillApp() ... killReason={0}

`HP3D` is the system's high-priority 3D watchdog. **This governs every diagnostic
you add.** Our `ORBIS_WAIT_CAP_NS` fence-slot wait is 5 s; the console kills at
roughly 1 s. That is why the wait-path dump added today has never fired, and why
`radv.log` ends mid-stream with the last *flushed* lines looking healthy — the
buffered tail dies with the process.

**Anything that waits longer than about a second will never be seen.** If you want
the wait-path dump, lower the cap for that path first.

Corollary: `PW_WINE64 alive` ticks showed `sink_calls` frozen at 5332 for the last
~3 s while `cpu_ms`, `audio` and `audible` kept climbing — the app was alive and
working right up to the external kill. There is no app-side fault to find.

## Fixed today, committed and pushed (`1db20a2`)

`src/mesa-patches-ps4/0003-orbis-dump-the-hang-that-kills.patch`:

1. **The dumper was a process-wide one-shot.** `static bool reported` latched on
   the first four-submission stall. In run 1 that stall was `#4997`, which
   **recovered** — the run went on for ~14,300 more submissions — so the hang that
   actually killed it (`#19323`) could never be dumped. It now re-arms whenever the
   fence label moves again, capped by `ORBIS_HUNG_DUMP_MAX` (4). This is what made
   run 2 show the real death burst (`#14058, #14062, #14068, #14072`).
2. **The fence-slot wait never dumped.** It is the path the fatal hang takes, and
   it printed numbers only. It now runs the same dump. (Still unproven in practice —
   see the HP3D section; the 5 s cap means it has not yet had a chance to fire.)
3. **The user-data block stated a false conclusion as fact.** It announced
   `THE WRITE RUNS PAST THE END OF THE MAPPING` from reading `COMPUTE_USER_DATA`
   slot 4 as `fill_memory`'s `max_offset`. Every compute pipeline writes those
   registers, so that reading is a guess — and it was wrong. It now prints the
   mapping, the launched grid and the assumption separately.

## Dead ends — do not re-run these

* **`ORBIS_HS_OFFCHIP_PER_SE` / the tess offchip ring.** No HS, ES or GS stage
  appears at the stop in any dump. These draws do not tessellate; the ring is
  allocated and never touched. The `VGT_HS_OFFCHIP_PARAM <- 0x00000100` warning
  with 4 SEs is real but not this bug.
* **The "4 GiB fill overrun" from run 1.** A misread (see fix 3). Run 2's dumps
  have user-data slots 2-5 **all zero** — there is no fill dispatch in those
  streams at all.
* **`radv_init_dcc()`'s `meta_size - size` underflow** (`radv_cmd_buffer.c:15962`).
  The obvious Neo-shaped suspect, but it is gated on `gfx_level == GFX8` and
  cannot run here: `amd_family.h` places `CHIP_LIVERPOOL` and `CHIP_GLADIUS`
  between `CHIP_KAVERI` and `CHIP_KABINI`, so **both Sony parts are GFX7**. Neo is
  not a different gfx level, only a different topology.
* **Gladius-specific surface code.** There is none — `ac_surface.c` and the RADV
  sources contain no `CHIP_GLADIUS` or `CHIP_LIVERPOOL` arm. Surface layout goes
  through generic GFX7 addrlib paths, so a Neo surface bug would have to come from
  wrong topology *input*, not a Neo-only code path.
* **`RESIDUE GREW` (the per-device leak).** Fires exactly once, at startup, across
  DXVK's device create/destroy cycles: 6 BOs and 4 syncobjs. It never recurs. 49
  BOs will not exhaust anything 19,000 submissions later.
* **Scratch sizing.** Checked and it is fine: `radv_device.c:1636` sizes scratch
  `32 * num_cu`, and the orbis arm reports `num_cu = num_se * 1 * 9` = 36 on Neo
  (measured — the Gladius patch moved the knee from 72 to 144 SIMDs). Scratch
  scales with the part.

## Still unadjudicated

* **`pa_sc_raster_config` is the live hypothesis** (above).
* `ac_orbis_drm.c` flags `ORBIS_NUM_SE` as an untested separator for a different
  question: the GSVS ring needs exactly twice what `32 * num_se` gives, which is
  either "this field should be 4" or "the ring size is per-SE". With the field now
  4 on Neo by default, that experiment's meaning has changed — re-read the comment
  at `ac_orbis_drm.c:6232` before using it.
* `GB_ADDR_CONFIG.NUM_SHADER_ENGINES` reads **one** on this hardware, which
  contradicts both the 2-SE and 4-SE settings. The file argues it is a tiling input
  and not the arbiter. Unresolved.
* Nothing here is measured from the silicon. `SQ_WAVE_HW_ID` carries
  `SE_ID`/`SH_ID`/`CU_ID`; a compute kernel that ORs one bit per `(SE, SH, CU)`
  would enumerate the real topology and settle the SE count, the CU bitmap and the
  raster-config question together. That is the measurement this whole area is
  waiting on, and it has never been run.

## Traps that have each cost a build

* A patch regenerated with `git diff` against the fully-applied tree carries
  context from later patches and will not apply at its own position. Fold the
  change into the patch that owns the code instead.
* `fprintf(stderr)` reaches **nothing** on this console — not one `wine-ps5:` line
  has ever appeared. Use `ERR()` in ntdll (works even from a TEB-less thread),
  `sceKernelDebugOutText` in wineserver (klog), and `mesa_log*` in the driver
  (which now reaches `radv.log` via the env loader).
* `pkill -f` / `pgrep -f` with a literal pattern kills the invoking shell. Use the
  bracket trick: `log-receiv[e]r.py`.
* `prospero-win/` is gitignored and is its own git tree. Work there survives only
  as patches in `src/prospero-win-patches-ps4/`. Same for `mesa-build/mesa-ps4/`
  and `src/mesa-patches-ps4/`. **Verify every patch with
  `git -C <tree> apply --check --reverse <patch>` before trusting it.**

**Leading mechanism, stated with its limits.** `migrate_exec_page_to_flex()`
in `src/native/pw_wine_dmem_glue_ps4.c` does this to a live 16 KiB granule:

    memcpy(saved, page, 0x4000);              // snapshot
    pw_wine_dmem_replace(..., 0);             // release direct memory -> unmapped
    sceKernelMunmap(page, 0x4000);            // drop the reservation -> unmapped
    mmap(page, ..., MAP_FIXED|MAP_ANON);      // fresh zero page
    memcpy(mapped, saved, 0x4000);            // restore the snapshot
    pw_wine_dmem_adopt(...);

There is **no locking anywhere in that file** (only atomics for log counters).
Between the release and the restoring memcpy the page is unmapped or
zero-filled, and any concurrent write by another thread is either faulted or
silently overwritten by the stale snapshot. In the 1012 klog this ran **570
times in a 9-second burst at 18:52:18-18:52:27, 102 seconds into the run** —
i.e. during active multithreaded gameplay, not during single-threaded image
load. Package 1016 did not remove this window; it made the previously failing
`mmap` succeed, so the migrations now complete instead of bailing out.

This is independently a real defect and it is title-agnostic. **It is not yet
tied to the observed crashes.** The gap is explicit: this function has one
caller, the executable-protection path, while the recurring faults are at guest
*heap* addresses (`0x06…`-`0x32…`). Corrupting a 16 KiB executable granule does
not directly explain a null vtable field on a heap object. Do not present this
as the cause until that link is established or ruled out.

Supporting but non-conclusive: patch `1000` exists precisely because a guest
fault was observed on a page that a fresh kernel query then reported as mapped
and writable — a transient-mapping signature consistent with a race of this
shape.

**Test attempted and its result.** Built `pkgout/ab-10167-no-exec-migration/`

It **crashes at startup with SIGILL** about four seconds in, 69 log lines:

    11:52:59.192  wine-ps4: exec mprotect addr=10000 bytes=16384 prot=0x5 sce=0 libc=0
    11:52:59.192  wine-ps4: dmem-exec-selfcheck build=0971 addr=10000 ... prot=0x1
    11:52:59.193  wine-ps4: exec-range flex-migrate complete addr=400000 bytes=16384
    11:52:59.196  # A user thread receives a fatal signal
    11:52:59.196  # signal: 4 (SIGILL)

**The per-page migration is load-bearing.** It exists to make executable pages
actually executable; leaving a granule as non-executable direct memory makes
the first instruction fetch illegal. The `prot=0x1` in the self-check line
(read-only, no execute) is the immediate cause. **It cannot be removed — any
fix must make it safe.**

Also learned: there are **two** migration paths, `exec-page` (per-page) and
`exec-range` (range-based). This test disabled only the first; `exec-range
flex-migrate complete` still appears in the klog. Any future attempt must
account for both.

The race hypothesis is therefore **still unproven**. The correlation is strong
but the window contains the whole RX cluster, not just the migration, and the
isolation test could not run.

**Suggested next step — prove or refute the race directly rather than by
removal.** Add a bounded diagnostic that records the address range and
timestamp of each migration, then at each guest fault checks whether the fault
address falls inside a recently migrated granule. If guest faults land in
pages migrated moments earlier, the race is demonstrated; if they never do, it
is excluded and attention moves to the rest of the RX cluster. This is
diagnostic-only and carries no risk of the SIGILL above.

A design alternative worth considering if the race is confirmed: migrate
executable pages **eagerly at image map time**, while startup is still
effectively single-threaded, instead of lazily on fault. The dangerous
migrations are the 570 observed in a 9-second burst 102 seconds into a run,
during live multithreaded gameplay.

#### 2026-10-28 BREAKTHROUGH: Fallout's crash is flexible-memory FRAGMENTATION

The `flexible_holder` telemetry separates Fallout from the titles that work,
and the discriminator is **mapping count, not bytes**:

    GTA IV  (works) : rank=1  bytes=183328K  count= 451  prot=0x7  anon:000800c3ee64
    Fallout (crash) : rank=1  bytes=154608K  count=4872  prot=0x7  anon:000800c3ee64
    Fallout also    : rank=5  bytes= 20960K  count= 128  prot=0x5  anon:000800c3ee64

Same caller (`0x800c3ee64`, inside `ntdll.prx` segment 0 at
`800b8c000-800c70000`), same protection, *less* total memory — but **10x the
mappings**. Fallout averages 31 KiB per mapping against GTA IV's 406 KiB.

Both titles map almost identical flexible totals (Fallout 476,192K, GTA IV
477,056K), so this is not a volume problem. The flexible pool is being
**shredded** for Fallout, and an allocation then fails despite ~60 MiB
nominally free because the free space is not usable in the shape requested.

**Mechanism.** There are two migration paths, and the checkpoint's own comment
states the split:

    /* Move a contiguous direct-memory span to flexible memory in one operation.
     * The per-page version above is retained only for mixed/sparse mappings where
     * a queried range is not wholly backed by direct memory. */
    static int migrate_exec_range_to_flex(uintptr_t address, size_t bytes)

GTA IV's executable regions are contiguous and wholly direct-backed, so they
take `migrate_exec_range_to_flex` — 451 large mappings. Fallout's are sparse or
mixed, so they fall back to `migrate_exec_page_to_flex` — 4,872 individual
16 KiB mappings.

This accounts for every prior observation:

- perfect correlation with the RX machinery arriving between 10080 and 10091
- Fallout's low `dmem` (131-143 MiB): executable pages are migrated *out* of
  direct memory into flexible
- `flexible_free` draining to 6-9 MiB and then a guest fault on a pointer that
  should be valid — an allocation returned NULL into Gamebryo code that does
  not check it
- why GTA IV and Oblivion tolerate the identical code

**Fix directions, in order of preference:**

1. **Coalesce in the per-page path** — batch adjacent pages that need the same
   protection into one mapping instead of one mapping per 16 KiB granule. This
   attacks fragmentation directly and leaves both paths intact.
2. **Teach `migrate_exec_range_to_flex` to handle sparse ranges** — migrate the
   direct-backed subspans as ranges rather than dropping the whole span to the
   per-page path.
3. Reduce how often migration is needed at all (eager migration at image map
   time, while startup is single-threaded).

**Acceptance criteria for any candidate:** Fallout NV reaches gameplay, and
**Oblivion and GTA IV must not regress** — both have fast reproducers and both
currently work on 10167. The measurable signal is the `flexible_holder rank=1
count` for `anon:000800c3ee64`: it should fall from ~4,872 toward GTA IV's
~451 without the byte total growing.

### Two reasoning errors behind it, both worth avoiding

1. **`heap_log_fallback` latches.** It opens with
   `if (__atomic_exchange_n(&heap_direct_fallback_logged, 1, __ATOMIC_RELAXED)) return;`
   — so it prints **at most one line per process, ever**, no matter how many
   millions of fallbacks occur. "Zero fallback lines in klog" therefore never
   meant "zero fallbacks". (It does mean zero here: the line is absent from
   every log, and the same `sceKernelDebugOutText` channel carries
   "prefers direct memory" nine times, so the channel works and the latch never
   fired. But that conclusion needs the channel check, not the absence alone.)
2. **A symbolized address is not a provenance proof.** `anon:000800c3ee64`
   resolved to `pw_wine_heap_memalign`, which was read as "the Wine heap mapped
   this". But `heap_map()` maps with `map_protection`, which is
   `CPU_READ_WRITE` (0x3) and is only ever upgraded to `CPU_GPU_READ_WRITE` —
   never `0x7`. A holder at `prot=0x7` cannot have come from `heap_map`. The
   protection contradicted the symbol and the symbol was believed anyway.

### Facts established while chasing it (these do hold)

- `heap_map()` has exactly two unlogged `return NULL` paths: the
  `getenv("WINE_PS5_HEAP_FLEXIBLE")` opt-out and a size-overflow guard that
  cannot fire. The opt-out string is absent from both the 10167 and 10080
  eboots, and `PW_WINE64_HEAP_FLEXIBLE` is a compile-time `-D` defaulting to 0.
- `heap_use_direct_memory()` is called once from `__wine_ps5_dmem_region()`
  when `state > 0`, and its banner appears 9× in klog, so the backing **is**
  registered and `backing.map` is not NULL.
- Therefore every `heap_map` call in these runs succeeded, and heap spans and
  large blocks are **direct** memory at prot 0x3 — not the flexible RWX bulk.
- `PwWineHeapStats` already counted `failures`, but **nothing ever logged it**,
  which is why an allocation failure was never observed either way.
- `log_flexible_holders()` filters on `info.flags & 1`, and bit 0 is
  documented in `wine64_main.c` as *flexible*, so the holder lines really are
  flexible-only. That part of the telemetry is sound.
- In `pw_wine_heap.c`, every **large** block (anything whose
  `bytes + HEADER + sizeof(LargeHeader)` exceeds the 64 KiB top size class)
  gets its **own** page-rounded mapping from `map()`. `pw_wine_heap_memalign`
  reaches that path readily because it calls `allocate(bytes + alignment)`.
  This is a real property of the allocator; it is simply not a Fallout/GTA IV
  discriminator.

```c
    unsigned long long live, peak_live, mapped, peak_mapped;
    unsigned long long allocs, frees, failures, foreign, large;   /* 9 x u64 = 72 B */
} heap = { 0 };
extern void pw_wine_heap_stats( struct pw_heap_stats *stats );
```

Adding five counters to `PwWineHeapStats` made `pw_wine_heap_stats` write
112 bytes into that 72-byte buffer — a 40-byte stack smash on the loader's
refusal path, which runs during startup. The Wine tree had been compiled at
12:28, before the 12:45 header edit, so the caller and callee disagreed about
the struct's size.

**Rule this establishes:** `PwWineHeapStats` has an **out-of-tree duplicate
declaration** and its layout is effectively frozen. Growing it requires a full
Wine rebuild *and* editing `loader.c`'s private copy in the same change.
Adding a counter is not a safe log-only change. `sizeof(PwWineHeapStats)` must
stay **72**; assert it if in doubt.

**Fix (1019).** The new counters moved into a separate `PwWineHeapFailures`
struct (40 B) with its own `pw_wine_heap_failures()` getter, leaving
`PwWineHeapStats` at 72 B. Both the glue and the heap link into `ntdll.prx`
under `-Bsymbolic`, so the new symbol needs no PRXDESC export. Verified by
compiling a `sizeof` probe, not by inspection. Host
`tests/test_pw_wine_heap.c` passes. `ntdll.prx` `537459ab…` (1018, broken) →
`410fe618…` (1019). Unstripped symbols for this runtime are preserved at
`run-ab-20261028/symbols-1019/` (11 `.shared.elf` files).

**Process note.** 1018 changed two things at once: the merged (never
hardware-validated) runtime *and* new instrumentation, against the A/B rule in
`AGENTS.md`. The stack smash fully explains 1018, so 1019 still carries both.
If 1019 also fails early, isolate the merge next rather than adding anything

### Live suspect: the exec-range migration (and this names it properly)

The rank-1 flexible holder in the 1020 run is
`anon:000800caf354  152,352K  count=4843  prot=0x7`, and `800caf354` matches the
`exec-range` callers in klog for the same run (`caller=800caf3b7` ×15,
`caller=800caf354` ×2). So the RWX flexible bulk comes from
**`migrate_exec_range_to_flex`**, not the Unix heap — `heap_anon=1` proves the
heap independently. 3,046 `exec-range` calls in this run alone.

(This supersedes the earlier guess that the bulk was `pw_wine_heap_memalign`;
that symbol never fit, because `heap_map` maps at `CPU_READ_WRITE` 0x3 and can
never produce `prot=0x7`.)

**Mechanism.** `migrate_exec_range_to_flex()` snapshots a span, unmaps it,
re-mmaps it, then copies the snapshot back — and there is **no locking anywhere
in `pw_wine_dmem_glue_ps4.c`** (only `__atomic` on log counters). Any concurrent
write landing inside that window is silently reverted to stale bytes. A reverted
pointer write corrupts an object reference, and the crash surfaces later wherever
that reference is used — which matches the varying site and the non-NULL garbage.
It is also consistent with Fallout working on the one build that lacks this
machinery.

The earlier "RX/exec-page migration ruled out" note does **not** contradict this:
that probe only showed the path runs without breaking GTA IV and Oblivion, which
migrate far less. It never tested a title doing thousands of migrations.

### A/B package 1021: exec migration disabled, nothing else changed

The gate already existed: `exec_migration_allowed = bytes <= PW_PS4_EXEC_MIGRATE_MAX_BYTES`
(`src/native/pw_wine_dmem_glue_ps4.c:878`, bound defined at :595, was 16 MiB).
Setting the bound to **0** makes it false for every nonzero request, so
`protect_exec_range()` — and the per-page fallback inside it — never runs, and
`PROT_EXEC` on dmem-backed memory falls back to plain `pw_wine_dmem_protect()`.

Rather than hand-edit the constant (easy to forget to restore, against the
additive rule in `AGENTS.md`), it is now `#ifndef`-guarded and
`scripts/prx-ps4.sh` passes `${PW_PRX_EXTRA_CFLAGS:-}` when compiling the glue.
1021 was linked with `PW_PRX_EXTRA_CFLAGS="-DPW_PS4_EXEC_MIGRATE_MAX_BYTES=0"`;
**the default build is unchanged**, so this reverts by simply not setting it.

Verified the define actually reached the compiler, rather than assumed: the glue
compiled with the define is `ac458e7df905058c7a00218827c6ed6e` and without it
`50220e75b81dd8efc88408bac730b358`, and the object linked into 1021's ntdll is
`ac458e7d…` — the OFF build.

**What to expect.** If migration is the corruptor, 1021 reaches gameplay and the
`prot=0x7` rank-1 holder collapses. Runtime confirmation that the gate is off:
every `exec-range build=…` line should read `fallback=skip-large` instead of
`fallback=bounded`. Oblivion and GTA IV must be re-checked on 1021 before this
becomes a fix, since they depend on exec protection working.

## 2026-10-28 BREAKTHROUGH: the faulting page is NOT PRESENT, and the migration's mmap is failing EINVAL

`available=64512K` free flexible and `flexible_holder rank=1 count=4767`
mappings. EINVAL with 63 MB free points at a kernel VM-entry limit, not memory
pressure — and the *scratch* mmap failing too (`mmap(NULL, 131072, RW,
PRIVATE|ANON)`) shows it is not specific to `MAP_FIXED`.

`migrate_exec_range_to_flex()` releases before it maps:

```c
release_rc = pw_wine_dmem_replace(&dmem, address, bytes, 0);   /* range UNMAPPED */
mapped = mmap((void *)address, bytes, PROT_READ|PROT_WRITE,
              MAP_FIXED|MAP_PRIVATE|MAP_ANON, -1, 0);          /* <-- EINVAL, 215x */
```

so each failure leaves a range that is unmapped in hardware and committed in
Wine. The faulting page is exactly such a hole — the migration walked the
allocation in 16 KiB steps and stopped one page short of it:

```
15:35:19.172  flex-migrate complete addr=272f0000 bytes=16384
15:35:19.172  flex-migrate complete addr=272f4000 bytes=16384
              (272f8000, containing 0x272f9af4, never migrated)
15:35:24.217  Unhandled page fault on read access to 272F9AF4
15:35:25.964  exec-range verify addr=272f8000 migrate=-1 protect=-1 effective=0x3
```

`migrate=-1` on that page confirms its migration failed.

### What this retroactively explains

- **Per-page migration (1022) made it worse**: it creates ~1000x more mappings,
  so it hits the VM-entry limit harder. It crashed earlier and differently.
- **Disabling migration (1021)** removed the holes but lost RX, dying at a
  prologue.
- **The constant ~133.5k minflt fault depth**: the failures begin when the
  mapping count crosses the limit, which happens at a reproducible point in the
  save load.
- The early "fragmentation" instinct was right in *substance* — mapping count,
  not byte count — even though the numbers first cited for it were bogus SDL
  event counters from an unrelated log.

### Fix, in two parts

1. **Never leave a hole (correctness).** The failure path attempts
   `pw_wine_dmem_replace(address, bytes, READ|WRITE)` and a `memcpy` restore,
   but **nothing logs whether that restore succeeded**, and a hole only persists
   if it did not. Instrument the restore result first, then make the path safe:
   either confirm a replacement mapping is obtainable before releasing, or treat
   a failed restore as fatal and loud rather than silently leaving committed
   memory unmapped.
2. **Stop hitting EINVAL (root cause).** 2,023 migrations produce thousands of
   individual flexible mappings; once the kernel's VM-entry table fills, mmap
   returns EINVAL regardless of free memory. Coalesce migrations, skip ranges
   already flexible, or reuse a pool so the mapping count stays bounded.

Part 1 stops the crash; part 2 stops the condition that triggers it. Do part 1
first — it is small, and it converts a silent memory-corruption bug into a
diagnosable failure.

### Retraction 2: nothing maps `0x400000` outside Wine's view tracking

`find_view_range()` was right; the range *is* free. `anon_mmap_tryfixed()`
(`virtual.c:974`) **synthesizes** the errno on the PS4 path:

```c
if (sceKernelReserveVirtualRange( &ptr, size, PS5_MAP_FIXED | PS5_MAP_NO_OVERWRITE, host_page_size ))
{
    errno = EEXIST;          /* any failure reason, reported as a collision */
    return MAP_FAILED;
}
__wine_ps5_dmem_region( start, size );   /* success path only */
```

So `mmap-eexist` means "the reservation was refused", never "occupied". Do not
go looking for a squatter again.

### Retraction 3: memory exhaustion was not ruled out

`dmem_failures=0` and `heapfail count=0` instrument **direct memory** and the
**Unix heap**. The *flexible* pool (~440 MB/title), where Wine's anonymous
`mmap`s land, has **no failure counter at all**. It is the pool that runs dry.

### What actually happens

Every genuine conflict has a size that is not a multiple of the 16 KiB host
page; the fourteen that are aligned are just the relocation scan doing its job:

| conflict | size | size % 16K | |
|---|---|---|---|
| `mmap-eexist base=400000` | `1009000` | **0x1000** | real |
| `view-range base=10000000` | `133000` | **0x3000** | real |
| `view-range base=10000000` | `9000` | **0x1000** | real |
| `view-range base=1..e000000` x14 | `600000` | 0x0 | normal scan |

`anon_mmap_tryfixed()` is the **only** PS4 reservation site that neither rounds
nor asserts host-page alignment (contrast `anon_mmap_fixed()` at 633-634,
`mmap_add_reserved_area()` at 808-809, and `ROUND_SIZE` at 677/697/737/2166/
2186/2457). On a 4 KiB host it cannot misbehave -- PE sections are always 4 KiB
multiples -- so this is PS4-specific and invisible upstream. The asserts never
fired because the reserve fails *first* and returns EEXIST.

One refusal causes all three symptoms:

1. **Relocation.** Fallout cannot take `0x400000`, so it moves to `0x530000`.
   Oblivion cannot relocate and dies at `c0000018` in `build_module()`.
2. **Exhaustion.** `__wine_ps5_dmem_region()` is on the success path, so a
   refused range is never registered; `__wine_ps5_mmap` then requires
   `MAP_FIXED` **and** a registered region (`pw_wine_dmem_glue_ps4.c:841`) to
   use direct memory, and everything there falls to flexible instead.
3. **Slowness.** Unregistered ranges commit one SIGSEGV per 16 KiB host page
   (`PW_SEGV_ENTRY` stepping down by exactly `0x4000` at a fixed `rip`) rather
   than in bulk via `pw_wine_dmem_replace`.

Measured, same log, same day:

```
GTA IV  (reaches gameplay)  dmem=858,720K   flexible_free plateaus 49,152K   survives
Fallout 1041                dmem peak 144,304K  flexible_free -> 10,240K     dies 3m35s
Fallout 1040                                    flexible_free -> 18,432K     dies 3m24s
Fallout 16:01 PRE-SYNC      at 0x400000         flexible_free ->  8,192K     dies 3m40s
```

The pre-sync run at `0x400000` dies the same way at the same time: **relocation
is not what kills Fallout, exhaustion is**, and it predates the sync.

### Package 1042

`host_size = ROUND_SIZE( start, size, host_page_mask )` before the reserve, used
for the reserve, `__wine_ps5_dmem_region()`, `anon_mmap_fixed()` and the
failure-path `munmap()`. Adds `PW_RESERVE refused base=.. size=.. host_size=..`,
which fires only when rounding mattered.

**`PW_RESERVE` is the package marker.** A Fallout run showing `mmap-eexist`
with no `PW_RESERVE` beside it is the *old* build -- confirmed at 18:18, when a
launch 1 minute after upload was still 1041 because the pkg had not been
installed.

Predictions, any failure of which kills the theory: Fallout loads at
`0x400000`; `dmem` share rises and `flexible_free` stops reaching zero; fault
count drops sharply. Oblivion is the cleanest test -- it dies before executing
an instruction, so it either loads or it does not.

Risk to watch: rounding reserves up to 12 KiB past an image tail. Wine rounds
its own view sizes identically (2166/2186), but a **new** conflict where there
was none is the signature of this going wrong. GTA IV works today and is the
regression check before Fallout is the win.

### CORRECTION to the section above: alignment was NOT the cause

The 16 KiB-alignment theory is **wrong** and package 1042 (which shipped it) is
a **no-op**. `map_fixed_area()` already rounds before calling:

```c
char *start = base, *end = (char *)base + ROUND_SIZE( 0, size, host_page_mask );
```

so the size reaching `sceKernelReserveVirtualRange` was always host-page
aligned. The `size=1009000` in a `pw_img_conflict` line is the **original image
size printed at the failure site**, not the value passed to the syscall. Do not
reason about syscall arguments from that number.

Method note, because this was the third wrong theory in a day: each one was
built by inferring a cause from a logged value. The one that worked was adding
a log line that prints what the kernel was actually asked and what it answered.
**Instrument the failing call before theorising about it.**

### Actual root cause (measured, package 1043, FW 12.02)

`sceKernelReserveVirtualRange` **never succeeds on PS4** as invoked here:

```
PW_RESERVE refused rc=0x8002000c base=400000 want=0x130000 host=0x130000 align=0x4000 got=400000 prot=0x3
```

- `rc=0x8002000c` -> low byte `0x0c` = **errno 12, ENOMEM**, not EEXIST.
- **54 of 54 refusals in one launch, all the same rc. Zero grants.**
- Smallest refused: `want=0x10000` (64 KiB) at `PROT_NONE`. A 64 KiB refusal
  with ~440 MiB free is the *call* being rejected, not a shortage.
- `want=0x130000` is already 16 KiB-aligned -- alignment dead a second way.

**`errno = EEXIST` in `anon_mmap_tryfixed()` manufactures the collision.**
Nothing ever occupied `0x400000`; `find_view_range()` was right all along. Every
hour spent hunting a squatter was spent chasing an errno we wrote ourselves.

Consequence chain, now evidenced rather than inferred:

```
reserve always fails
  -> reserved_areas stays empty
  -> mmap_add_reserved_area() and __wine_ps5_dmem_region() never run
  -> map_fixed_area() always fails      -> Fallout relocates to 0x530000
                                        -> Oblivion dies c0000018 (cannot relocate)
  -> no range is dmem-backed            -> all of it lands in the ~440 MiB
                                           flexible pool -> dry at ~3.5 min
```

The decisive asymmetry: **plain `mmap` succeeds at these same addresses** --
that is how `FalloutNV.exe` loads at `0x530000` seconds after the reservation
of `0x400000` is refused.

### Package 1044

On refusal, fall back to `mmap` + verify-the-address-returned, which is what
the generic branch of `anon_mmap_tryfixed()` already does on every other
platform, then call `__wine_ps5_dmem_region()`. The PS4 kernel ignoring
MAP_EXCL was the reason the reservation was preferred; verify-after-map covers
that case.

**Scoped to `prot != PROT_NONE` on purpose.** `reserve_area()` requests
PROT_NONE blocks up to 1.7 GiB to claim address space. If PS4 charges flexible
memory on mmap regardless of prot, honouring those would consume the whole pool
at startup -- worse than the refusal. Bulk reservation stays refused; only real
mappings take the fallback. **Abort signal: `flexible_free` well below 448512K
in the first startup lines means mmap charges flexible and the guard was
wrong.** Measure that before widening the fallback to PROT_NONE.

### Still unknown

Why the PS4 kernel returns ENOMEM for a 64 KiB fixed reservation at all. Flag
values (`PS5_MAP_FIXED` 0x10, `PS5_MAP_NO_OVERWRITE` 0x80) and the
`host_page_size` alignment argument are the untested variables; a standalone
probe that sweeps flags and alignment and prints rc would answer it directly,
and would be cheaper than another full package.

## 2026-10-28, 19:15 -- THE regression: the eboot was never released

`0x400000` *was* occupied, and by us. Package 1045's query at the failure site:

```
query rc=0 start=400000 end=49c000 qprot=0x5 qtype=0 qflags=0x11 name=executable hole=0
```

**`name=executable` is our own eboot**, mapped 0x400000-0x49c000. The kernel's
ENOMEM was honest: you cannot reserve over the running executable. Retract the
claim two sections above that nothing was ever there -- `find_view_range()`
tracks Wine's views, which never included the host executable.

`src/reloc-wine-app/app_entry.c` already solves this:
`pw_relocated_wine_release_eboot()` unmaps the eboot's low segments right
before the guest starts. That is the whole reason the eboot is tiny and the
app lives in a high PRX.

**The upstream sync dropped the call site.**
`src/reloc-wine-app/0001-delay-eboot-release-until-game-start.patch` was never
reapplied to `prospero-win/native/wine64_main.c`: the function sat exported and
uncalled, and there are **zero `relocwine:` lines in the entire day's log**.

```
pre-sync   release runs  -> 0x400000 free -> 19 consecutive loads at 0x400000 (09:00-16:01)
post-sync  release gone  -> eboot squats  -> Fallout -> 0x530000; Oblivion -> c0000018
```

Restored in **1046**. Expect `relocwine: unmapping eboot seg0 0x400000..0x49c000`
and `PW_WINE64 relocatable eboot release status=0` within the first seconds.

This is NOT expected to fix the flexible-memory exhaustion: the pre-sync 16:01
run loaded at 0x400000 and still died at 3m40s with 8 MiB free. That is an
older, separate bug.

### Why the sync census missed it

The census covered `src/prospero-win-patches-ps4/` and `src/wine-patches-ps4/`.
**`src/reloc-wine-app/` sits outside both.** Any future sync must check every
`*.patch` in the repo, not just the numbered series.
